03 / WHAT CAN BE CLAIMED

现在能证明什么，也明确不能证明什么。

Execution evidence

可以保留 dispatch started / settled / failed，以及 result delivery/admission 是否成功的区别。执行成功不再自动等价于模型看到了结果。

Delivery & bytes

可以区分 measured delivery bytes、unknown legacy evidence 和 delivery rejection，并对单次 run 的 delivered-result budget 做一致推导。

Replay evidence

可以重建历史 request input 并保留 request-scoped reproducibility evidence，同时避免把 live fork 和 reproducible replay 混成同一种语义。

Benchmark evidence

可以验证 paired observation、failure state、fixture digest 和 deterministic replay。它不会制造真实 benchmark 数据，也不会自动判断 Code Mode 更优。

35 / 35最终 benchmark integration 的 Fork CI static gates：35 passed、0 failed、0 skipped；focused job 同时通过 benchmark Python tests、execution accounting、delivery-byte、admission、replay 与 trajectory suites。
04 / NEXT PHASE

下一步不是再拆三条 feature 线。

第一阶段的基础设施已经进入主干。接下来更有价值的是把它们串成稳定的开发者工作流，并开始使用真实、可追溯、可复核的数据做实验。

P0 / INTEGRATE

整合 developer diagnostics

把 execution summary、trajectory inspection 与 replay evidence 串起来，同时维持 run-local 与 global/session claim 的证据边界。

P1 / EXPERIMENT

运行可复现实验

真实 benchmark 使用 attributable inputs、validated result pairs、failure taxonomy 与 inspectable reports；结论留在 experiment 层。

P2 / UPSTREAM

持续控制 fork drift

有意识地 sync/rebase upstream，优先保留小而清晰的 package/plugin seams，不积累没有必要的 fork-only privileged architecture。

Guardrail / 非目标

基础设施完成不等于模型或 execution mode 的胜负结论。没有 reproducible inputs、validated pairs、explicit failure handling 与 inspectable reports，就不应该把任何“更快 / 更省 / 更好”的说法包装成证据。
