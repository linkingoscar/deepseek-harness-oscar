01 / ENGINEERING PRINCIPLES

Fork 的开发思想

保留上游 “Everything is a Plugin” 的架构，把增量集中在可审计执行与可复现实验上，而不是重新造一个 privileged core。

01 / EVIDENCE

Evidence before interpretation

先持久化足以解释一次 run 的事实，再做诊断、归因和性能结论。

02 / DELIVERY

Execution 与 delivery 分开记

工具执行成功，不代表结果一定被接纳、传回模型或被完整计量。证据必须保留这些差异。

03 / OBSERVE

诊断默认不改变行为

Accounting 和 DevTools 优先作为 behavior-neutral observation layer，避免“为了看清运行时而改了运行时”。

04 / REPLAY

Replay 是明确的语义契约

Live fork、reproducible replay 与 effect-free simulated replay 不混为一个按钮。

05 / BENCHMARK

先验证 benchmark harness

Pair schema、fixture、deterministic replay、consistency check 和 failure taxonomy 比“先给一个分数”更重要。

06 / UPSTREAM

小而清晰的扩展 seam

尽量沿现有 package / plugin seam 演进，让改动可测试、可审查，并保持 upstream-friendly。

03 / ACTIVE WORKSTREAMS

现在正在推进什么

三条 branch 从同一主线基线切出。这里描述的是开发范围，不把尚未合并的能力写成既成事实。

agent/execution-devtools-diagnosticsACTIVE SCOPE

Execution diagnostics

把已有 accounting/evidence 升级为可以快速解释 trajectory 的诊断面。原则上只增强可观察性，不改变 runtime 行为。

deliveryRejected把交付拒绝变成一等诊断信号。
byte accounting让 measured / unmeasured / rejected 的 bytes 可区分。
peak concurrency从 durable evidence 得到并发峰值。
orphan dispatch识别 unsettled / orphan dispatch。
per-tool summary按工具聚合执行、交付与失败证据。
behavior-neutraldiagnostics 默认不注入语义变化。
agent/replay-reproducibility-evidenceACTIVE SCOPE

Replay reproducibility

继续收紧 replay 所依赖的 inputs、snapshots、effects 与 outputs，让“可复现”能够被证据证明，而不是靠“看起来一样”。

input provenance明确 replay 实际使用的历史输入。
snapshot evidence记录 snapshot 身份与重建依据。
effect semantics区分 live effects 与 effect-free execution。
output evidence让 replay 输出可归因到对应执行路径。
agent/offline-benchmark-validationACTIVE SCOPE

Benchmark validation

目标不是先产出漂亮分数，而是先证明 benchmark harness 自己可靠：结果成对、来源明确、失败可分类、报告可复核。

paired schema显式表示配对结果、provenance 与 failure state。
fixtures用 deterministic replay 验证 harness。
consistency对不一致结果执行结构化检查。
failure taxonomy把基础设施失败与任务失败区分开。
report generation报告从 validated results 生成。
no fake score基础设施存在 ≠ 性能结论成立。

04 / ROADMAP

从 evidence 到 reproducibility

路线图按基础能力依赖排序：先把事实记准，再把 replay 做实，最后才让 benchmark 结论具有可审计性。

P0

Trustworthy execution evidence

补齐 rejected delivery、bytes、concurrency、unsettled/orphan work 和 per-tool summary。

P1

Reproducible replay

收紧 historical snapshots、replay inputs 和 deterministic/effect-free regression paths。

P2

Validated benchmark harness

建立 paired schema、fixture、consistency checks、failure taxonomy 与 report generation。

P3

Upstream-friendly integration

保持 package/plugin seam 清晰，控制 fork-only architecture，持续与 upstream 对齐。

05 / EVIDENCE MODEL

一次 run 应该如何被解释

诊断不是从最终输出倒推故事，而是沿 durable evidence 逐层回答：发生了什么、什么被交付、什么被拒绝、能否重放、结论是否可验证。

01

Dispatch

谁被调度、参数是什么、是否存在未 settle 的工作。

02

Execute

工具是否真正执行成功，耗时/失败属于哪一层。

03

Delivery

结果是否被 admission、拒绝，bytes 是否可测。

04

Persist

model-visible 信息与 replay 所需事实进入 session evidence。

05

Replay

明确 live fork / reproducible / simulated 的不同语义。

06

Validate

只有可复核的 paired result 才能进入 benchmark report。

deliveryRejected 是交付层事实，不应该被改写成“工具执行失败”；这类语义区分正是本 fork 的核心工作之一。
伪造 benchmark 数字用 instrumentation 存在本身证明 Code Mode 更强把 runtime 行为修改藏进 diagnostics为 fork 重写 Cordis / plugin 架构
